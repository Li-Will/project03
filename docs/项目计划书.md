## 1. 项目背景与目标

### 1.1 业务痛点（简历里的"为什么"）
- 客服系统常见问题：**意图混杂**（FAQ / 报障 / 投诉 / 闲聊混在一起），一条消息要人肉分类路由；
- **工单无状态管理**：人工客服凭记忆跟进，状态靠口头，容易漏单、超 SLA、无审计；
- **AI 答非所问**：FAQ 检索答非所问却不转人工，客户体验差（**该转人工时不转**是客服 AI 最大的隐形事故）；
- **不可运营**：解决了多少个、转人工率、SLA 达成率这些运营指标没有自动化采集。

### 1.2 项目目标（可量化，全部要真实跑出来）
1. **意图路由**：在线评测集中业务意图分类准确率 ≥ 90%（rule + LLM 混合）；
2. **客服解决率**：FAQ 类在模拟评测 ≥ 85%，且**引用命中率 100%**（答非所问宁可转人工）；
3. **转人工决策质量**：评测集的「该转」/「不该转」人工标注 F1 ≥ 0.85（**本项目最有说服力的评估点**）；
4. **SLA**：P1 工单在模拟时间轴内升级/到期提醒全部按预期触发；
5. **状态机**：任意非法状态迁移 100% 被拒绝并记录审计；
6. **端到端**：FAQ 直答 < 1s（本地 Qdrant），诊断工单 < 15s，转人工 → 人工回复 → resume 恢复闭环可演示。

### 1.3 非目标（明确砍掉，防止范围蔓延）
- **不做**真实 IM 接入（企业微信/钉钉/Slack 对接留到 M4 后，MCP 化即可一句带过）；
- **不做**真实客服坐席系统（排班/绩效/坐席工作台）——人工接管用 API + 演示页模拟；
- **不做**语音/多模态（纯文本）；
- **不做**真实线上流量——评测基于「模拟客户会话集」离线 + 回放，**明确声明不是真实用户数据**（诚实边界，见 §11）。

## 2. 技术选型与理由（每一条都是面试弹药）

| 技术 | 选型理由（面试直接背） |
|---|---|
| **LangGraph** | 工单的每一步都是图节点：状态更新节点保证「先入库再让 Agent 干」，条件边做意图分支，`interrupt()`/`Command(resume=...)` 原生支持「转人工挂起→人工回复→恢复」，Checkpoint 落 SQLite 支持崩溃恢复——状态机 + Agent 一套图表达 |
| **FastAPI** | 异步 + 自动 OpenAPI + SSE 流式（`/api/v1/chat`）；统一 `trace_id`（= 会话/工单 id）贯穿检索与 Agent 轨迹 |
| **SQLite + SQLAlchemy** | 工单/消息/客户/评论/SLA 审计五张表，单文件零运维（简历说「业务数据落库」够用）；**Checkpoint 也用 SqliteSaver**，一套存储 |
| **Qdrant（本地模式）** | FAQ 知识库向量检索；**复用 project01 踩坑经验**（客户端/服务端版本对齐；本地模式免 Docker，纯 python 即可跑通，降低交付门槛）；`QDRANT_MODE=local` |
| **LLM 双模式** | 云端 OpenAI 兼容端点（deepseek-v4-flash-0731，project01 `.env` 经验）+ **无 key 时规则分支确定性降级**（意图分类用规则词典，方案生成用模板 + 检索片段拼接）——「没有 LLM 也能演示核心链路」 |
| **pytest** | 状态机迁移表单测 + eval 评测集批量跑，CI 离线可跑 |

**决策原则**：任何新增依赖先问「减掉它行不行」。本项目的差异化不是堆技术栈，是**状态机的确定性与多 Agent 的灵活性如何共存**——所以 SQLite/Qdrant-local 都是降运维的选择，把复杂度集中在状态机与路由逻辑上。

## 4. 数据模型（核心：工单状态机）

### 4.1 工单状态机（本项目最核心的确定性资产，面试必讲）

```
        new ──► in_triage ──► processing ──► resolved ──► closed
          │                    │   ▲            │
          │                    ▼   │            │
          │                pending_user ◄──────┘   （等用户补充/确认）
          │                    │
          │                    ▼
          │                escalated ◄──────── new/in_triage/processing/pending_user
          ▼                    │
      rejected（意图误判/无效）┘
```

- **合法迁移表写死**（`states.py` 枚举 + `TRANSITIONS` dict），任何 Agent/API 试图非法迁移（如 `closed → processing`）→ 抛 422 + 审计日志；
- **状态是数据库里的真值**，Agent 无权直接改状态——只能通过「状态更新节点」走校验后更新。**规则与 Agent 的边界就在这里**；
- 转人工 = `interrupt()` 挂起在 `processing`，人工接管后写 `pending_user`（等客户）或直接 `resolved`，再 `Command(resume=...)` 恢复图继续。

### 4.2 SQLite 表

| 表 | 字段要点 |
|---|---|
| `customers` | id, name, tier(普通/VIP), created_at |
| `tickets` | id, customer_id, intent, category(品类), priority(P1/P2/P3), state, sla_deadline, assignee(agent|human), created_at, updated_at |
| `messages` | id, ticket_id, sender(customer|agent|system), content, source(faq/diagnosis/human/template), created_at |
| `ticket_events` | id, ticket_id, from_state, to_state, actor, reason —— **状态迁移审计，转人工决策留痕** |
| `reviews` | id, ticket_id, rating(1-5), comment —— 满意度闭环 |

### 4.3 LangGraph State

```python
class TicketState(TypedDict, total=False):
    request_id: str
    customer_text: str
    intent: str                      # faq/ticket/complaint/chat/need_human
    category: str
    priority: str
    ticket_id: str                   # 建单后回填
    faq_hits: list                   # 检索候选（标题+片段+来源）
    faq_confidence: float
    diagnosis_steps: Annotated[list, add_messages]   # 诊断轨迹（评估用）
    solution: str
    citations: Annotated[list, add_messages]          # [n] 引用编号
    human_action: dict                # interrupt 返回的人工指令
    state: str                        # 同步工单状态（只经校验节点更新）
    error_log: Annotated[list, add_messages]
```

## 5. 多 Agent 设计（角色边界 = 面试题素材）

| Agent | 职责 | 输入 | 输出 | 工具 | 关键指令 |
|---|---|---|---|---|---|
| **Intent Router** | 意图分类 + 建单与否 | 用户消息 | intent + 置信度 | 规则词典(优先), LLM(兜底) | 「低置信不许猜，返回 need_human」 |
| **Ticket Classifier** | 工单要素抽取 | 消息 + 客户档案 | category, priority(P1-P3), 概要 | 规则(关键词/SLA 语义) | P1 判断：支付失败/数据丢失/账号被盗等 |
| **FAQ Answerer** | FAQ 直答 | 消息 | 引用片段 + 置信度 + 直答/转人工标记 | Qdrant 检索 | 置信度 < 阈值 → 标记转人工，不编答案 |
| **Diagnostic Agent** | 复杂工单多步排查 | 工单 + 首次检索 | 诊断轨迹 + 根因假设 | 知识库检索/历史工单检索 | ReAct 循环，最多 N 步，步间引用来源 |
| **Solution Writer** | 方案生成 | 诊断轨迹或 FAQ 命中 | 带 [n] 引用的回复 | 模板 | 每条回答必须有引用；无引用 → 返回「需人工」 |
| **Escalation Triage** | 转人工决策（校验层） | 上方输出 + 状态 | 转人工理由 / 继续直答 | 规则(置信度/情绪/P1/权限) | 「该转不转」是事故，「不该转转了」是浪费，两条都要评测 |
| **SLA Scheduler** | 后台升级（非图内） | 全表扫描 | 到期/临近升级事件 | asyncio 任务 | 写 `ticket_events` + 触发提醒消息 |

**与 project02 的对照（面试要主动讲的）**：project02 是固定流水线（Planner→Data→…→Reviewer 一条线，流程确定）；project03 是**意图驱动的分支路由**（一条消息可能走 FAQ 直答、也可能走诊断链、也可能直接转人工）——两种拓扑没有优劣，取决于「业务步骤是否固定」。**这个对照本身比任何一个 Agent 更能证明你理解多 Agent 编排的本质**。

## 6. 核心流程与工程机制

### 6.1 主流程（面试执行链路原样讲）
```
用户消息 → POST /api/v1/chat → Intent Router
  ├─ 置信度低 → need_human → 直接回「转人工」模板（不建单）⚠️ 绝不硬猜
  ├─ faq     → FAQ Answerer → 置信度达标 → 带引用直答（≤1s）→ 结束
  │            └─ 不达标 → 转人工（建单 escalated）
  ├─ complaint → 建单 + 直接转人工（不自动答，标记情绪/优先级）
  ├─ chat    → 品牌话术模板（不建单）
  └─ ticket  → 建单(in_triage) → Ticket Classifier(类/优先级)
             → Diagnostic Agent 多步排查(最多 N 步, 轨迹入 diagnosis_steps)
             → Solution Writer 生成带引用方案
             → Escalation Triage 复查：仍低置信/涉权限 → interrupt 转人工
             │      人工接管：写 pending_user → 用户确认 → resolved → 满意度(review) → closed
             └─ 高置信 → 方案直接回复 → 待用户确认 → resolved → review → closed
```
要点：**用户的「确认/拒绝」通过 `/human-reply` 提交回来，人工接管也用同一端点（actor=human vs 用户）**，把「人工接管」和「用户确认」统一成一个 resume 入口——少一个分支，多一份可审计性。

### 6.2 转人工（HITL 完整形态，对比 project02 的审批闸门）
- project02 是「风险分高 → 等审批 → 继续」，一次性闸门；
- project03 是**流程内任意节点可转人工**：FAQ 低置信、诊断步数耗尽、方案无引用、P1 事件、用户要求人工、投诉——都收敛到同一个 `interrupt({type:"escalate", reason})`；
- 恢复：人工回复（`/human-reply`）→ resume → 图上从挂起节点继续（更新状态 + 发消息），**状态机保证转人工后不会「回炉重跑已经做对的部分」**。

### 6.3 SLA 与优先级（运营向，面试「业务指标」弹药）
- P1(≤30min) / P2(≤4h) / P3(≤24h)：建单时定，调度器每 5min 扫 `sla_deadline`；
- 临近(80% 时限) → 写入 `escalated` 升级事件 + 提醒消息；
- 超时 → `escalated` + 审计；演示页/API 暴露 `GET /admin/escalations` 队列。
- **SLA 与状态机合流**：升级事件也是一次「状态迁移」，走 4.1 的校验表，非法迁移同样拒绝。

### 6.4 防幻觉红线（客服场景 = 幻觉零容忍场景）
1. FAQ 直答必须有**置信度阈值**，不达标绝不硬答（答错 = 客户投诉，比转人工贵 100 倍）；
2. Solution Writer 强制「每条主张带 [n] 引用」，无引用段落 = 不输出该段，整段空 → 转人工；
3. `answer 引用编号必须存在于本次检索集合`（复用 project01 RA-3 思路，做生成后校验）；
4. 生产声明：「本系统为模拟环境评测，回答仅供演示，不构成真实服务承诺」——README 免责。

### 6.5 异常兜底（复用 project02 三层兜底模式，缩到两层） 
| 层 | 措施 |
|---|---|
| 工具/Agent 层 | 检索失败 → 空命中走转人工（客服场景「无据不答」）；LLM 调用失败 → 规则降级（意图用词典、方案用模板）；JSON 解析失败重试 1 次 |
| 链路层 | 图级 timeout + 步数上限；任意致命错误 → 工单 `failed` + 审计 + 「请稍后再试/转人工」兜底文案 |

## 9. 评估方案（M3，面试第 30–40 题素材）

**三层目标 × 两类集合**：
- **离线 gold set**（80 条，含「转人工」人工标注）：意图准确率、FAQ 解决率、引用命中率（RA-3 简化版）、转人工 F1、平均步数、P50/P95、单会话 token；
- **在线模拟回放**：把 80 条按「客户会话脚本」跑完整闭环，输出运营指标——解决率 / 转人工率 / 首次响应时间 / SLA 达成率 / 满意度分布。
- **可靠性与局限**：gold set 由「2 个产品线 FAQ + 自造客户话术」构成，误导、多轮、投诉、闲聊全部标注 schema 化；**明确声明是模拟会话不是真实用户**——样本量小，结论只作工程/回复质量参考，不声称「生产级客服指标」。

**转人工决策质量（本项目特色指标）**：
- 金标准：每条 gold set 人工标注 `should_escalate ∈ {yes, no, optional}`；
- 指标：`该转没转`（事故，权重大）× `不该转转了`（浪费，权重小）→ F1；
- 这是**客服 AI 与「答非所问却自信满满」的分界点**，面试讲这一条 = 「我懂客服 AI 的命门」。

## 10. 风险与应对

| 风险 | 概率 | 应对 |
|---|---|---|
| FAQ 语料不够「真实」、评测过拟合 | 中 | 语料覆盖 2 个产品线 + 边界（歧义/多轮/双关）；明确声明模拟会话 |
| 转人工决策规则难定 | 中 | 先规则后 LLM：置信度/情绪/P1/权限关键词四路信号投票，gold set 人工标注兜底 |
| LLM 无 key 时演示降级 | 高 | 规则版 Intent Router + 模板方案，核心链路（建单/状态/SLA/转人工）完全不依赖 LLM |
| 状态机与 LangGraph 集成复杂度 | 中 | 先做纯数据库状态机 API（M1），再接图（M2）——图只负责「决策」，状态真值永远在库 |
| 时间不够 | 中 | 明确可砍项见 §8；MVP 先保证「FAQ 直答 + 转人工 + 状态机」三角色闭环 |
| 面试被问「这项目是不是重复造轮子（客服有现成产品）」 | 必被问 | 口径：定位是「用 LangGraph 演示企业级工单 Agent 的完整生命周期与评估方法」，重点在状态机/转人工/SLA 的工程化设计，不是做一个可商用的客服产品 |

## 11. 诚实边界（写进 README 与口稿）

1. **模拟数据**：客户、会话、满意度均为脚本生成，**非真实用户**；指标只证明「系统在本评测集上的行为」，不声称生产指标；
2. **不做真实 IM/坐席集成**：人工接管是 API + 演示页模拟，对接企业微信/钉钉属 M4 之后的方向（MCP 化一句带过）；
3. **评测集规模小**（≈80 条）：效果结论带置信度标注，不写「准确率 99%」这种无法复现的话术；
4. **客服场景不是纯技术问题**：免责声明「回答仅供演示，涉及资金/隐私/法律问题一律转人工」是系统设计的一部分，不是免责话术。
